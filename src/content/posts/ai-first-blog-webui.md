# 面向 AI 的博客管理界面

本文介绍 Cyber先锋社使用的内容管理服务，以及它如何把 AI 对话接入博客维护。阅读需要了解 HTTP 接口、前后端分离、Markdown 与 Git 等基本概念，不要求熟悉 Agent 框架。

## 从内容文件开始

这套管理界面独立于博客仓库运行，前端使用 Svelte 5 与 Vite，后端使用 Hono 与 Zod。内容本身是 Markdown 或 MDX 文件，顶部带 YAML front matter，版本由 Git 管理。界面覆盖四类内容：posts 文章、dynamic 社团动态、projects 成员资料、spec 独立页面。

AI 对话没有另起写入通道。普通表单、Markdown 编辑器与 AI 对话共用既有的后端管理接口；模型通过 OpenAI 兼容的 Chat Completions 接入，可调用 list_content、get_content、get_site_status、get_templates 和 propose_change。前四个用于读取内容、站点状态与模板，最后一个只准备提案，不直接写文件。模型没有 shell、任意文件访问、账号或密钥管理工具。

权限与责任因此留在服务端。模型理解需求、读取资料、把结果组织成结构化字段；是否落盘由用户确认，再由后端调用原有的 CRUD 或发布接口。一次对话可以连续调用多个读取工具，但每次修改都要经过同一条提案通道。

## 指令如何进入操作卡片

以“给一位成员补上 GitHub 链接”为例。模型先用 list_content 找到 projects 集合中的目标成员，再用 get_content 读取资料，确认现有 link 数组与其它字段，然后调用 propose_change 提交 operation、collection、slug、data 与 reason。若需求换成“为一篇文章整理摘要”，读取对象变成 posts，data 中只带 description，正文与其它元数据保持原样。

```text
自然语言需求
   ↓
list_content / get_content / get_templates 读取资料
   ↓
propose_change 生成结构化提案（每轮最多 6 个）
   ↓
界面展示字段变化与正文对比
   ↓
用户点击确认或输入「确认执行 1」
   ↓
后端按服务器保存的编号取回提案，调用原 CRUD / 发布接口
```

下面只保留工具参数的关键结构，地址为占位内容：

```json
{
  "operation": "update",
  "collection": "projects",
  "slug": "member-example",
  "data": {
    "link": [{ "label": "GitHub", "icon": "fa7-brands:github", "value": "https://github.com/example" }]
  },
  "reason": "根据成员公开主页补充社交链接"
}
```

提案生成后，界面展示字段变化和正文对比。用户输入「确认执行 1」时，前端先把界面上的操作序号映射为服务器生成的随机编号，再向确认接口提交该编号；后端据此取回原提案，不接受客户端重写操作参数。因此界面看到的内容与真正执行的内容来自同一份服务端记录。提案 15 分钟内有效，服务重启会失效；重复确认已完成的操作会返回原结果，不会再次提交。每轮最多 6 个提案，避免一次对话堆积过多待审操作。

## 让写入经过检查

提案只是待执行状态，写入前还有检查。Zod 负责字段 schema 校验；后端核对目标内容指纹是否与准备提案时一致；原接口自带乐观锁；Git 写入通过串行队列执行。任何一环发现内容已经变化，本次写入都会被阻止，用户需要重新读取并生成新提案。

| 环节 | 检查内容 | 失败时的结果 |
| --- | --- | --- |
| 准备提案 | 字段 schema、集合白名单，以及 slug 的格式和存在性条件 | 不生成可执行提案 |
| 执行前 | 目标内容指纹是否与准备时一致 | 阻止覆盖，要求重新读取 |
| 写入 | 原接口乐观锁、串行 Git 写入队列 | 冲突时中止本次提交 |
| 发布 | 仓库 HEAD 是否与预期一致 | 条件不满足则不继续发布 |

这些措施针对常见的并发与误覆盖问题，属于具体工程约束，不能理解为模型永远不会犯错。内容在准备提案后被别人修改，系统会阻止覆盖；摘要是否准确、字段是否合适，仍要由确认者判断。

保存有实际变更的内容时，后端落盘并创建 Git 提交；推送是独立动作，会触发托管平台构建。推送成功仍需核对构建与部署结果。文章或成员的创建提案默认使用草稿；草稿即使推送也不会在博客前台公开，需要先将 draft 改为 false，再保存并推送。spec 独立页面只能维护已有路由所读取的内容文件，新建 spec 文件不会自动产生前台路由。系列归属与章节序号属于文章字段，需要在元数据中设置。

## 表单仍然有用

编辑器提供 9 个 Markdown 模板，覆盖技术教程、技术分享、活动通知、成员主页、关于页面等常见结构。AI 侧提供排版、润色、续写、提纲、正文、标题摘要标签建议。建议先以预览形式出现，用户确认后才应用到编辑区；应用之后仍需保存。编辑器保留 AI 与模板的撤销入口，生成期间如果原内容被修改，旧建议不会覆盖新的编辑。

交互表单可以逐项核对成员字段与文章元数据，本地文件上传则需要在界面选择文件。成员资料使用博客兼容的字段格式：

| 字段 | 用途 | 示例 |
| --- | --- | --- |
| title | 成员名称 | 张三 |
| description | 简介 | 关注 Web 安全与后端开发 |
| status | 自由状态，推荐 member / 在校 / 已毕业 | member |
| order | 排序，数字越大越靠前 | 10 |
| tags | 角色与技能标签 | ["后端", "运维"] |
| link | 社交链接数组 | [{label, icon, value}] |

AI 也能为角色、排序、状态和社交链接生成修改提案，表单则让管理员逐项核对取值；两种入口复用相同的数据结构和后端校验。图标使用博客已安装的命名空间，例如 fa7-brands:github、fa7-solid:globe、fa7-solid:envelope，或 material-symbols、simple-icons、mdi、mingcute，不使用 fa6 图标。成员资料不应包含虚构的学校、学历或履历。

## 记录模型调用的代价

AI 设置需要填写接口地址、模型 ID、密钥与兼容参数。密钥保存在服务端 .env，文件权限 0600；它不会回显到界面，不写入浏览器持久存储，不进入 Git，也不会被放进模型提示词。需要说明的是，.env 文件不是加密保险箱，能读取服务器文件的人仍可拿到密钥。模型可以自动获取、搜索选择或手动填写；原生工具能力不足时可切换到 JSON 指令模式，两种模式最终都经过同一套提案校验。连接诊断会检查模型列表、真实文本生成，并可选执行不写入内容的工具兼容测试。

Token 用量按每次模型请求记录。一轮对话如果包含多次工具循环，需要累计输入、输出和总量；缓存与推理属于细分项，不能重复加总。usage 缺失时界面显示未上报，不能当作零。监控只包含本 CMS 上线后发起的请求，不等于服务商总账单。系统支持每日与月度额度、预警，并在达到额度后阻止后续请求；正在进行的请求和尚未上报的用量仍可能造成超额。

当前对话和待确认提案只保存在内存中，刷新或重启后的恢复能力有限；执行结果有单独日志，但不是完整的会话持久化。这套界面适合有人值守的内容维护，不应被理解为永久记忆、完全自动运维，或能控制全站任意功能。它处理的是把 AI 的读取与建议纳入可审阅、可回滚的内容管理流程，边界之外的事情仍由人和既有运维流程负责。
